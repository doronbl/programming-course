# Scaffolding review: programming-course infra + backend + SPA (v1)

This pass scaffolds the whole product skeleton in a monorepo: five CloudFormation stacks (network/VPC+ALB, REGIONAL WAF, S3+CloudFront, Cognito Google-only auth, ECS Fargate-SPOT compute), a FastAPI backend with Cognito JWT verification and one protected `/api/hello`, and a static-exported Next.js SPA that drives Cognito Managed Login (OAuth2 code + PKCE) with a single button that calls the protected endpoint. The locked decisions are respected across the board — Google is the only IdP, the client is public (no secret) with PKCE, the SPA is `output: 'export'` with no SSR/Lambda@Edge, the `/api/*` CloudFront behavior uses the CachingDisabled managed policy, and the ECS service runs on FARGATE_SPOT.

Watch for: **(blocking, confirmed)** the SPA's entire client logic — `frontend/lib/auth.ts` and `frontend/lib/config.ts` — is silently excluded from git by the root `.gitignore`'s Python `lib/` rule, so a fresh clone cannot build the frontend. **(confirmed)** the internet-facing ALB accepts `0.0.0.0/0` on :80, so the WAF's per-IP rate limit and IP reputation logic aggregate on CloudFront edge IPs rather than real client IPs, and the ALB is directly reachable bypassing CloudFront. **(likely)** CloudFront→ALB origin is HTTP-only, so Bearer tokens traverse the CloudFront→ALB hop in cleartext.

**Verdict**: NEEDS_CHANGES

## High-level view

The frontend is broken at the repository level, not the code level. The SPA logic under `frontend/lib/` is well written, but the repo's root `.gitignore` is the stock GitHub Python template, whose `lib/` entry matches `frontend/lib/`. Both `auth.ts` and `config.ts` are untracked; `frontend/app/page.tsx` imports `@/lib/auth`, so anyone cloning the repo gets a build that fails on missing modules. The static verification that "npm run build passed" ran against the working tree, which still has the files locally — it cannot catch a tracking gap.

The trust boundary around the ALB is looser than the design implies. CloudFront is meant to be the front door, but the ALB security group allows HTTP from the whole internet, so the backend is reachable directly. The WAF is correctly associated with the ALB, but because requests arrive via CloudFront, the rate-based rule and any IP-based managed-rule logic key off CloudFront's edge addresses, not the caller's — the rate limit is effectively per-edge-node, not per-user.

The Cognito JWT path verifies the RS256 signature against JWKS, enforces issuer/expiry, and checks `token_use` + client id, accepting both access (`client_id`) and id (`aud`) tokens — no bypass.

The five stacks line up: every `Fn::ImportValue` matches an exported name, the ECS service registers to the network stack's target group, container port 8000 and health path `/health` are consistent across network/compute/backend, and the storage→auth `AppUrl` ordering is documented (the deploy guide also flags the ECR chicken-and-egg: the repo is created by the compute stack but the image must exist first).

3. **WAF rate limit keys on CloudFront IPs** — with WAF on the ALB and traffic arriving via CloudFront, `RateBasedStatement` with `AggregateKeyType: IP` aggregates on edge IPs, not clients. Add an HTTPS:443 listener (the `CertificateArn` path already exists) and switch the origin to `https-only`, or document the residual risk.
5. **Frontend uses access token; backend accepts either** — `callHello` sends `tokens.accessToken`, which lacks `email`/`profile` claims. Fine for `/hello`, but the id token is the one carrying user identity for future content APIs; note the intended token per endpoint before more routes are added.

### The SPA's logic is not in the repository

`frontend/app/page.tsx` imports `login`, `register`, `logout`, `callHello`, `getTokens`, and `handleRedirectCallback` from `@/lib/auth`, and `lib/auth.ts` in turn imports `loadConfig` from `./config`. Both files exist on disk and are correct, but neither is tracked:

```
$ git check-ignore -v frontend/lib/auth.ts
.gitignore:17:lib/	frontend/lib/auth.ts
```

The root `.gitignore` is the stock GitHub Python template; its `lib/` line (intended for `build/`, `dist/`, `lib/` Python packaging output) matches `frontend/lib/` because the pattern is unanchored. Result: the diff under review contains `page.tsx`, `config.json`, `next.config.js`, and `package.json`, but not the module that implements the entire OAuth2 + PKCE flow and runtime config loading. A fresh clone resolves `@/lib/auth` to nothing and the TypeScript build fails.

This is exactly the class of defect static verification misses — `npm run build` was run in the author's working tree, where the ignored-but-present files still resolve. The fix is two parts: force-add the files, and re-scope the ignore rule (anchor it as `/lib/` at repo root, or remove it, since the repo isn't shipping a Python package). Both `frontend/lib/auth.ts` and `frontend/lib/config.ts` need to land in the commit; nothing else in `frontend/lib/` should be swept in.

### WAF association vs. where requests actually enter

The WebACL is REGIONAL and associated with the ALB, carrying the common rule set, known-bad-inputs, and a per-IP rate-based rule at 2000/5min. Because CloudFront sits in front and proxies `/api/*` to the ALB, the source IP the ALB (and therefore WAF) sees is a CloudFront edge address, not the end user. The rate-based rule then limits aggregate traffic per edge node — many distinct users behind one edge share a bucket, and a single abusive client is spread across edges. IP-reputation components of the managed groups are similarly blunted.

```
client ──▶ CloudFront edge (real client IP here)
               │  forwards /api/* (edge IP is now the source)
               ▼
             ALB ──▶ WAF sees edge IP, not client IP
```

Two viable directions: attach the WebACL to the CloudFront distribution instead (scope `CLOUDFRONT`, created in us-east-1 — which this stack already is), where WAF sees the true viewer IP; or keep it on the ALB but switch the rate rule to `AggregateKeyType: FORWARDED_IP` with a `ForwardedIPConfig` so it reads `X-Forwarded-For`. The CloudFront-scoped option is the stronger posture for a CloudFront-fronted app.

### The ALB is a second, unprotected front door

`AlbSecurityGroup` permits `0.0.0.0/0` on port 80. The design treats CloudFront as the entry point (SPA + `/api` proxy), but nothing forces traffic through it — the ALB DNS name is public and directly reachable. The WAF still applies to direct hits, but the SPA-fallback error mapping and caching semantics live on CloudFront, and direct ALB access defeats the "single front door" model. Lock the ALB SG to the CloudFront origin-facing managed prefix list and have the origin send a secret header that the app (or an ALB listener rule) requires, so only CloudFront-originated requests are served.

### Cleartext backend hop

The `/api/*` origin config is `OriginProtocolPolicy: http-only` to port 80, so the Bearer token travels the CloudFront→ALB leg unencrypted inside AWS. The template already has a `CertificateArn`-gated HTTPS:443 listener on the ALB; wiring the origin to `https-only` when a cert is present closes this. (The behavior correctly forwards `Authorization` via the AllViewer origin request policy and disables caching via the CachingDisabled policy, so the API-uncacheable and token-forwarding decisions are met.)

### Token choice, access vs. id

`callHello` sends `tokens.accessToken`; the backend accepts both (`_verify_client` checks `client_id` for access tokens and `aud` for id tokens, and the tests cover both). For `/hello` this is immaterial. Worth fixing intent before the content API arrives: the id token carries `email`/`name`, the access token carries scopes/groups — pick per endpoint deliberately rather than defaulting to whichever the SPA happens to send.
