# Scaffolding review: programming-course front-door hardening + git-tracking fix (v2)

This pass addresses the v1 NEEDS_CHANGES findings. The blocking git-tracking defect is fixed: the stock Python `.gitignore` build-dir rules are now root-anchored (`/lib/`, `/build/`, `/dist/`, …), a Node/Next.js ignore section was added, and `frontend/lib/auth.ts` + `frontend/lib/config.ts` are committed — a clean clone can now build the SPA. The ALB is no longer a second open front door: its security group ingress is scoped to the CloudFront origin-facing managed prefix list, and an optional shared-secret `X-Origin-Verify` header (fixed-response 403 default action + priority-1 forward rule) gates the listener. The WAF rate limit now keys on `FORWARDED_IP`/`X-Forwarded-For`, and the CloudFront→ALB origin protocol is driven by a `BackendCertificateArn` param with the cleartext residual risk documented.

Watch for: **(confirmed, non-blocking)** front-door hardening is opt-in — the default deploy leaves `OriginVerifySecret` empty, so the ALB listener forwards unconditionally and the only barrier is the prefix list, which admits traffic from *any* CloudFront distribution, not just this one. This is documented as "recommended" in DEPLOY.md and acceptable for a scaffolding deliverable, but it means the shipped default is not the hardened posture.

## High-level view

The v1 blocker is genuinely resolved. `git ls-files` shows both TypeScript modules tracked, `git check-ignore` returns nothing for them, and the ignore rules now match only top-level Python build artifacts while `node_modules/`, `.next/`, and `frontend/out/` stay ignored. No other application source is swept up by the `lib/` pattern.

The ALB trust boundary is tightened in two independent layers. The security group now admits only the CloudFront origin-facing prefix list instead of `0.0.0.0/0`, and when an origin-verify secret is configured the listener default action returns 403 while a priority-1 rule forwards only requests carrying the matching `X-Origin-Verify` header. The header CloudFront sends (`OriginCustomHeaders` on the `/api/*` origin) and the value the ALB rule matches both dereference the same `OriginVerifySecret` param, so the two stacks stay in lockstep as long as the operator passes the same value to both.

The WAF change is coherent with a CloudFront-fronted ALB: `FORWARDED_IP` with `HeaderName: X-Forwarded-For` reads the viewer IP CloudFront appends rather than the edge IP the ALB terminates, so the rate limit is per end-user again. The WebACL stays REGIONAL on the ALB, and the `/api/*` behavior uses the managed AllViewer origin request policy, which forwards `X-Forwarded-For` (and `Authorization`) to the origin.

The no-cert default path is intact: every new parameter defaults to empty (or the well-known prefix-list id), the `!If` conditions collapse to the pre-existing HTTP-only, forward-everything behavior, and cfn-lint passes on all five templates with exit 0. The previously-sound areas are untouched — compute.yaml and auth.yaml are byte-identical to v1, and backend/main.py changed only by a docstring documenting the access-vs-id token intent.

The root `.gitignore` now anchors every Python build-dir rule to the repo root (`/lib/`, `/lib64/`, `/build/`, `/dist/`, `/wheels/`, …) with an inline comment explaining that the unanchored `lib/` was what swept in `frontend/lib/`. `git ls-files frontend/lib/` returns both `auth.ts` and `config.ts`; `git check-ignore -v frontend/lib/auth.ts frontend/lib/config.ts` returns nothing (exit 1). Build outputs remain excluded: `git check-ignore` still matches `node_modules/`, `.next/`, `frontend/out/`, `dist/`, and `build/`, via the new root-anchored rules plus a dedicated Node/Next.js section (`node_modules/`, `.next/`, `frontend/out/`, `next-env.d.ts`, `*.tsbuildinfo`). The per-package `frontend/.gitignore` is unchanged and consistent. The class of defect that hid this in v1 — verification running against a working tree that still had the files locally — is closed because the files are now committed, not merely present.

### ALB front door: prefix list + shared-secret header

Two layers replace the v1 `0.0.0.0/0` ingress. The security group now sets `SourcePrefixListId: !Ref CloudFrontPrefixListId` (default `pl-3b927c52`, the us-east-1 origin-facing list) on both the :80 rule and the cert-gated :443 rule. On top of that, when `OriginVerifySecret` is set the listener default action becomes:

```
DefaultActions: !If
  - HasOriginVerifySecret
  - - Type: fixed-response      # 403 "Requests must transit CloudFront"
  - - Type: forward             # open (dev/default)
```

and a priority-1 `ListenerRule` forwards only requests whose `X-Origin-Verify` header equals `!Ref OriginVerifySecret`. The storage stack sends exactly that header via `OriginCustomHeaders` on the `alb-api-origin`, dereferencing its own `OriginVerifySecret` param. The two are only consistent if the operator passes the same value to both stacks — DEPLOY.md calls this out and shows generating one secret reused across both `deploy` invocations.

The residual gap is that this layer is off by default. With the secret empty, the ALB forwards everything and the sole barrier is the prefix list — which is shared by all CloudFront distributions, so another account's distribution could in principle reach this ALB. For a source-plus-valid-template scaffolding deliverable this is acceptable documented risk, not a blocker, but the shipped default is the un-hardened posture and the hardened one requires an operator action.

### HTTPS listener rule asymmetry

The HTTP rule (`HttpOriginVerifyRule`) is gated on `HasOriginVerifySecret`, so it only exists when it can do something useful. The HTTPS rule (`HttpsOriginVerifyRule`) is gated on `HasCertificate` instead, and its match value is `!If [HasOriginVerifySecret, !Ref OriginVerifySecret, 'disabled']`. When a cert is present but no secret is set, the rule is created and matches the literal string `'disabled'` — no real request carries that, and the default action already forwards, so the rule never changes behavior. It's inert rather than incorrect, but gating it on `HasOriginVerifySecret` would drop the placeholder and make the two listeners symmetric.

### WAF rate limit keys on the viewer IP

The rate-based rule switched from `AggregateKeyType: IP` to `FORWARDED_IP` with `ForwardedIPConfig: { HeaderName: X-Forwarded-For, FallbackBehavior: MATCH }`, metric renamed `RateLimitPerForwardedIp`. Because the WebACL stays REGIONAL on the ALB and requests arrive via CloudFront, reading `X-Forwarded-For` recovers the real client IP that CloudFront appends, so the limit is per end-user rather than per edge node. `FallbackBehavior: MATCH` means a request without a parseable `X-Forwarded-For` counts toward the limit (fail-toward-blocking under the rate rule) rather than being exempted — the conservative choice for a rule whose header CloudFront always sets.

### CloudFront→ALB origin protocol

The `/api/*` origin's `OriginProtocolPolicy` is now `!If [ApiOriginHttps, https-only, http-only]`, where `ApiOriginHttps` is true when `BackendCertificateArn` is non-empty. Default (no cert) stays `http-only`, and DEPLOY.md's "Residual risk: CloudFront-to-ALB transport" section documents that Bearer tokens traverse that hop in cleartext inside the AWS network on the default path, with the remediation (set `BackendCertificateArn` to the same ACM cert used for the ALB HTTPS listener). The `/api/*` behavior keeps CachingDisabled and the AllViewer origin request policy, so caching-off and Authorization-forwarding are unchanged from v1.

### No regression in previously-sound areas

`git diff 586d602 HEAD` shows compute.yaml and auth.yaml unchanged, so FARGATE_SPOT, the S3 task role, port-8000/`/health` consistency, the Google-only IdP, the public PKCE client, and Managed Login are all as reviewed in v1. backend/app changed only by the `/hello` docstring documenting token intent (no behavior change); the JWKS/RS256/issuer/expiry/token_use/client-id verification path is untouched. The frontend static export (`output: 'export'`, no SSR/Lambda@Edge) and the OAuth2+PKCE redirect flow are unchanged apart from an added header comment. cfn-lint on all five templates exits 0.
